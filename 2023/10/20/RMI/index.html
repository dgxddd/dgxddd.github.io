RMI

RMI（Remote Method Invocation，远程方法调用） 是 Java 原生的分布式通信技术，允许一台 JVM 上的对象，调用另一台 JVM 上对象的方法，就像调用本地方法一样简单。

RMI 通信分析

创建远程服务

首先创建远程服务对象本身

然后会进入该类构造方法，super()调用父类UnicastRemoteObject构造

进入UnicastRemoteObject构造函数中并对port 传入了 0。其中port=0 不是使用端口 0，而是让系统自动分配一个可用的随机端口。

如果服务端的实现类没有继承 UnicastRemoteObject ，则需要手动调用 UnicastRemoteObject 的 exportObject 方法。跟进exportObject。把普通 Java 对象变成可远程调用的对象，port 传 0 就是自动分配端口，最终返回一个可被远程访问的代理对象

继续跟进exportObject，先判断对象是否为 UnicastRemoteObject 实例，若是则将负责网络通信的核心 UnicastServerRef 赋值给对象的 ref 属性，为其绑定通信能力，然后继续调用 sref.exportObject

跟进sun.rmi.server.UnicastServerRef#exportObject(java.rmi.Remote, java.lang.Object, boolean)，并在createProxy中创建一个能通过网络调用服务端方法的 “远程替身对象。

首先获取这个实现类实现的远程接口，如果没实现任何远程接口，直接抛异常。 判断是否使用固定编译好的Stub类，如果需要，就创建传统Stub。然后获取获取类加载器，获取实现类的所有远程接口，创建调用处理器：真正负责网络通信、发请求、收结果。最后用JDK动态代理，生成远程代理对象。

然后回到exportObject 方法，然后封装 Target 对象：把【服务实例、通信器、代理、对象ID】打包成一个目标。后开启网络监听、端口绑定、发布服务。分析一下如何开启的

然后跟进sun.rmi.transport.LiveRef#exportObject，可以知道ep是TCPEndpoint对象

继续跟进sun.rmi.transport.tcp.TCPEndpoint#exportObject其中又调用了TCPTransport的exportObject方法

继续跟进sun.rmi.transport.tcp.TCPTransport#exportObject，主要做了，启动服务器Socket，开始监听端口。调用父类方法，把Target注册到全局服务表。

首先跟进sun.rmi.transport.tcp.TCPTransport#listen，验证线程锁 → 创建 ServerSocket 并绑定端口（port=0 自动分配）→ 启动专门的接收线程循环监听客户端连接，同时处理端口占用、监听失败等异常，是服务端真正开启网络服务的核心操作。

跟进sun.rmi.transport.Transport#exportObject ，给 target 设置当前传输通道（TCP 通信层），标记服务由当前传输层提供，将服务目标存入 RMI 全局对象表

创建注册中心

首先来到java.rmi.registry.LocateRegistry#createRegistry(int)，我们跟进RegistryImpl这个对象中去。

判断是否在 RMI 注册中心端口（1099）上启动监听，且启用了安全管理器，是 RMI 对注册中心做的专属安全校验逻辑

如果没开安全管理器，它创建了一个LiveRef，以及创建了一个新的UnicastServerRef，跟进之后发现和之前是一样的，也是先赋值，然后进行exportObject()方法的调用。

继续跟进sun.rmi.server.UnicastServerRef#exportObject(java.rmi.Remote, java.lang.Object, boolean)，获取服务实现类的 Class 对象，并创建远程代理 Stub，再将服务实例、通信引用、代理封装成Target，通过底层引用完成端口监听与服务注册，最后返回代理对象供客户端远程调用。

跟进sun.rmi.server.Util#createProxy查看一下如何创建的过程，其中forceStubUse和ignoreStubClasses默认为falsestubClassExists(remoteClass)检查是否存在 XXX_Stub.class 类，比如 remoteClass=RegistryImpl就检查 RegistryImpl_Stub 是否存在。然后进去找到、加载、创建出 RegistryImpl_Stub 这个类的实例，然后返回给调用方

跟进sun.rmi.server.Util#createStub，主要通过反射加载并实例化 XXX_Stub 静态类，返回一个带通信信息的远程代理对象

继续回到sun.rmi.server.UnicastServerRef#exportObject(java.rmi.Remote, java.lang.Object, boolean)，如果当前生成的代理对象是【老式静态 Stub】（比如 RegistryImpl_Stub），那就给服务端安装【骨架 Skeleton】。

跟进sun.rmi.server.UnicastServerRef#setSkeleton。然后这里有一个createSkeleton()方法，一看名字就知道是用来创建 Skeleton 的

跟进sun.rmi.server.Util#createSkeleton，这个方法就是给老式 RMI 服务端，按固定命名规则（类名_Skel）找服务端骨架调度类

继续返回到sun.rmi.server.UnicastServerRef#exportObject(java.rmi.Remote, java.lang.Object, boolean)继续执行来到Target 的地方，Target 部分的作用也与之前一样，用于储存封装的数据，并在这里也封装了skel

服务端获取 Registry 代理对象

bind 是首次注册，如果服务名已经存在，会直接抛出AlreadyBoundException异常，不允许覆盖；

rebind 是覆盖注册，无论服务名是否已存在，都会用新的服务对象替换掉旧的，不会抛异常，直接覆盖。

Server 端和 Registry 在同一端

Server 端通过本地调用获取 Registry 对象。此时，Server 端获取到的 Registry 对象是 RegistryImpl 类的实例，这是 RMI 的默认实现类。服务器大多数情况下与注册中心 Registry 在同一端。其中这里的 registry 就是 RegistryImpl 对象

安全校验，确保调用者有权限注册

我们使用的rebind看看是如何添加的，跟进java.util.Hashtable#put，将远程对象放入了 RegistryImpl 内部的 HashTable 集合中。

Server 端和 Registry 不同端

当 RMI 服务端（Server）与注册中心（Registry）部署在不同进程或不同机器时，服务端无法直接获取 Registry 真实对象，只能通过网络获取一个代表远程注册中心的代理对象。这个对象就是 RegistryImpl_Stub，它是 RMI 内置的静态代理类，内部封装了 Registry 的通信地址、端口与远程调用逻辑。

在不通端的时候可以发现获取的是RegistryImpl_Stub对象

跟进 RegistryImpl_Stub 的 rebind 方法，先通过RemoteRef创建RemoteCall远程调用对象，通过序列化流将服务名、远程服务对象转为字节数据，随后调用invoke，done

UnicastRef 的 newCall 方法返回一个 RemoteCall 对象，用来给 invoke 方法提供参数

服务端通过调用 RegistryImpl_Stub 的 rebind 方法，将参数序列化发送到 Registry 端，来完成将服务接口绑定到注册表的操作。

当服务端与注册中心处于不同节点时，服务端通过RegistryImpl_Stub发起的远程请求会经由网络发送至 Registry 端，sun.rmi.transport.tcp.TCPTransport#handleMessages 作为 RMI 底层网络处理入口负责持续监听端口、接收 TCP 连接与数据流，并将接收到的请求转交给serviceCall方法

跟进sun.rmi.transport.Transport#serviceCall，serviceCall 是 Registry 端远程请求分发核心方法，它从客户端请求流中读取 ObjID 定位目标远程对象，通过 ObjectTable 获取对应的服务目标与 Dispatcher 调度器，在权限与类加载器上下文校验后，调用 disp.dispatch(impl, call)

dispatch 方法又调用 UnicastServerRef 自身的 oldDispatch 方法，跟进 UnicastServerRef 的 oldDispatch 方法：

oldDispatch 是 Registry 端远程方法调度的核心实现，它从客户端请求流中读取调用标识与方法编号，校验通信一致性后，将请求转交给 RegistryImpl_Skel

这是 RegistryImpl_Skel#dispatch 中处理 rebind 注册服务的核心逻辑：先从客户端请求流中反序列化出服务名称与远程服务对象，调用真实注册中心实现 RegistryImpl.rebind() 将服务存入内存 Map 完成绑定。

客户端的服务调用

客户端获取 Registry 对象的方法与服务端远程获取 Registry 的方法一样

其中客户获取的也是RegistryImpl_Stub 对象

RegistryImpl_Stub的lookup客户端实现，通过RemoteRef创建远程调用对象，将客户端需要查询的服务名序列化并通过网络发送至注册中心；调用invoke发起远程请求后，等待并反序列化注册中心返回的服务端 Stub 对象

同样来关注 Registry 端的处理逻辑，与 Server 端调用 rebind 方法时 Registry 端的处理逻辑相同，最终都是调用 RegistryImpl_Skel 的 dispatch 方法来处理。lookup 方法对应的是 RegistryImpl_Skel 的 dispatch 方法中的 2 号处理逻辑

调用流程

代理对象的任意方法被调用，都会触发 RemoteObjectInvocationHandler 的 invoke 方法RemoteObjectInvocationHandler 的 invoke 方法最终其实是调用 RemoteRef 的实现类 UnicastRef 的 invoke 方法。UnicastRef 中保存了服务端的地址和端口信息，这些信息是在服务端导出远程对象时设置的。因此 Client 端直接与 Server 端进行通信。
